# Регистрация загрузок P08

`RegistrationService` принимает Markdown text либо поток PDF/Markdown и публикует
проверенный immutable source через `BlobStore` до регистрации в БД. SHA-256
считается хранилищем по исходным байтам, text кодируется в UTF-8. Репозиторий
принимает только валидированный `UploadRequest`; при прямом использовании
репозитория вызывающий обязан предварительно сохранить source.

`ArticleRepository.register()` выполняет одну managed write transaction:
проверку Idempotency-Key, поиск актуального hash, создание Article при
необходимости, ArticleRevision, Job и Outbox, обновление указателей и сохранение
исходного ответа. Внутри callback нет файловых операций, HTTP или брокера;
драйвер может безопасно повторить откатившуюся транзакцию. Бизнес-конфликты
возвращаются через `RegistrationError` с безопасным кодом и `HTTPStatus`.
HTTP endpoints добавляются в P17.

## Идентичность и повторы

- Без article_id сравнивается только `Article.latest_source_hash`. При нескольких
  совпадениях выбирается минимальная строка UUID. Историческая, в том числе
  активная, ревизия не используется для определения актуального входа.
- С article_id проверяется только указанная статья. Неизвестный ID — not_found;
  равный hash — no-op; другой hash — новая ревизия с последовательным номером.
  Совпадение hash с другой статьёй не перенаправляет явное обновление.
- No-op возвращает существующие article/revision/job ID и текущий статус,
  в том числе failed, без новой ревизии, job или outbox.
- Idempotency-Key имеет scope app_id. Fingerprint включает article_id, включая
  отсутствие, метод text/file, тип содержимого и hash. MIME приводится к нижнему
  регистру без параметров; text/plain и text/markdown остаются разными типами.
  Имя файла не передаётся репозиторию и не участвует в fingerprint.
- Replay имеет приоритет над no-op и воспроизводит сохранённые код и body,
  даже после изменения статуса, retry или регистрации следующего содержимого.
  Другой fingerprint с тем же ключом — idempotency_conflict. TTL отсутствует.

## Конкуренция и состояние

Схема P08 добавляет uniqueness `RegistrationLock.name`. Перед использованием
репозитория нужно выполнить `init-schema` и стандартную readiness-проверку.
Все регистрации и ручные retry сначала получают эксклюзивную блокировку
единственного `RegistrationLock {name: 'uploads'}`. `MERGE` под uniqueness
защищает создание самого lock; запись свойства удерживает блокировку до commit.
Состояние читается отдельными запросами после получения блокировки. Это
защищает также отсутствие статьи при конкурентной первой загрузке.

Регистрации разных статей тоже выполняются последовательно. Это осознанное
ограничение текущей реализации; нагрузочные гарантии не измерялись.
Singleton нельзя удалять во время работы приложения. Тесты гонки его создания
делают это только на отдельной БД до запуска конкурентных операций.

Для существующей статьи дополнительно блокируется Article. Будущие операции
публикации и смены состояния должны сначала блокировать ту же Article перед
чтением указателей/изменением Job. Порядок регистрации: singleton → Article;
операция, уже удерживающая Article, не должна затем запрашивать singleton.
`get()` также использует короткую транзакцию с блокировкой Article, чтобы
вернуть согласованные latest/active/job/status/error. Worker, lease, публикация
результата и superseded относятся к следующим шагам.

`Article.latest_revision_id`, `latest_revision_number`, `latest_source_hash` и
`job_id` описывают последний запрос. `active_revision_id` регистрация не меняет.
Состояние и безопасная ошибка читаются из Job последней попытки. При failed
обновлении предыдущий успешный результат остаётся активным.

`retry()` разрешён только для последней failed-ревизии: создаёт новый Job с
attempt=0 и Outbox, переводит указатели Article/ArticleRevision на новую попытку,
сохраняет старый failed Job и не создаёт ревизию контента. Конкурентно принимается
один retry; остальные получают retry_conflict. Outbox имеет status=pending,
available_at в Unix seconds и job_id. Доставка относится к P16.

Файловая система и Neo4j не имеют общей транзакции. После ошибки регистрации
или конфликта может остаться непривязанный immutable source; он не удаляется,
поскольку тот же blob может использоваться другой статьёй. Будущая уборка
должна учитывать ссылки из всех сохранённых ревизий.
